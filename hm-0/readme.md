## ADR-001: Happy Cat Box

---

## Контекст

- Тестировщики спустя три месяца работы начинают работать с меньшей отдачей.
- Кол-во протестированных устройств падает с пяти в день до одного.
- Выявили причину: утомляемость.
- Для решения этой проблемы компания happy cat box создала дочку make cats free, минимизирующая лишнюю работу
  тестировщиков, за счет делегирования рутинных задач.
- Планируется масштабирование системы на крупные города по всей планете
- Обеспечение 99% матчинга игрушек между котами
- Бизнесу необходим низкий TTM
- Критично проверять новые гипотезы, проводить A/B тесты
- Система должна разрабатываться небольшим количеством работников, для сокращения расходов на бизнес и чтобы сходилась
  юнит-экономика

## Решение

- Реализация модульного монолита внутри каждого бизнес-контекста 
- Для каждого контекста, отдельная база данных
- Коммуникация между модулями внутри монолита обеспечивается за счет services layer, а между модульными монолитами по HTTP (REST)
- [Общая диаграмма с элементами, из которых состоит система](https://miro.com/app/board/uXjVJ7tOZvw=/?share_link_id=808233048409)

## Обоснование
- Модульный монолит обеспечивает вначале быструю и недорогую разработку, помимо этого позволяет
  сохранить low coupling и при изменении процессов внутри проекта можно будет распиливать на отдельные сервисы
- Выбрана одна общая база внутри определенного модульного монолита для избежания проблем связанных с транзакционностью между модулями
- Коммуникация по REST выбрана из-за простой интеграции и низкой нагрузки на систему

## Альтернативы
- Реализация микросервисов сразу. Но появляется сложность управления всем этим набором, плюс дороже по инфре и избыточно при низком кол-ве разработчиков
- Единый монолит. Усложняет масштабирование

## Спорные места
- Из-за общей базы внутри монолита, может возникнуть сильная связанность
- При росте нагрузки модули которые отвечают за матчинг может стать bottle neck в системе и тогда придется их выносить либо докидывать ресурсов
